# Bug Fix Documentation
## CORS Error Preventing Frontend-Backend Communication

**Date:** 2025-11-03  
**Version:** v01  
**Project:** Reading List Tracker (Mod 0001-reading-list)  
**Severity:** High (blocking development)  
**Status:** ✅ Resolved  
**Time to Fix:** 30 minutes

---

## Summary

Frontend application could not communicate with backend API during development. All API calls were failing with CORS (Cross-Origin Resource Sharing) errors in the browser console.

---

## The Problem

### What Happened

After setting up both frontend (Vite dev server on `localhost:5173`) and backend (Express server on `localhost:3001`), all fetch requests from the React app to the API were failing.

### Error Messages

**Browser Console:**
```
Access to fetch at 'http://localhost:3001/api/books' from origin 'http://localhost:5173' 
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on 
the requested resource.
```

**Network Tab:**
- Request Status: `(failed) net::ERR_FAILED`
- Type: `CORS error`

### When It Occurred

- **Context:** Day 5 of development, right after completing backend API endpoints
- **Trigger:** First attempt to load book list from frontend
- **Impact:** Complete blocker - frontend couldn't fetch any data

### What We Tried First (Didn't Work)

1. ❌ **Refreshing the browser** - Error persisted
2. ❌ **Restarting backend server** - No change
3. ❌ **Checking API endpoint URL** - URL was correct, backend was running
4. ❌ **Testing API directly with Postman** - API worked fine (CORS only affects browsers)

---

## Root Cause

CORS is a browser security feature that blocks requests from one origin (domain/port) to another. 

**Our situation:**
- Frontend origin: `http://localhost:5173` (Vite dev server)
- Backend origin: `http://localhost:3001` (Express server)
- **Different ports = different origins = CORS policy applies**

The Express backend was not configured to allow requests from the frontend's origin, so browsers blocked all API calls.

---

## The Solution

### Step 1: Install CORS Middleware

In the backend project:

```bash
cd server
npm install cors
npm install --save-dev @types/cors
```

### Step 2: Configure CORS in Express Server

Updated `server/src/server.ts`:

```typescript
import express from 'express';
import cors from 'cors';

const app = express();

// CORS configuration
const corsOptions = {
  origin: 'http://localhost:5173', // Allow Vite dev server
  credentials: true,
  optionsSuccessStatus: 200
};

app.use(cors(corsOptions));

// Rest of middleware and routes...
app.use(express.json());
// ... routes, etc.
```

### Step 3: Restart Backend Server

```bash
# Stop the server (Ctrl+C)
# Start it again
npm run dev
```

### Step 4: Test in Browser

Refreshed the frontend app - API calls now working! ✅

---

## Why This Worked

The `cors` middleware adds the necessary HTTP headers to API responses:

```
Access-Control-Allow-Origin: http://localhost:5173
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type
```

These headers tell the browser: "Yes, requests from `localhost:5173` are allowed."

## Alternative Solutions Considered

### Option 1: Vite Proxy (Frontend Solution)

Instead of CORS middleware on backend, configure Vite to proxy API requests:

```typescript
// client/vite.config.ts
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3001',
        changeOrigin: true
      }
    }
  }
});
```

**Why we didn't choose this:**
- Still need CORS for production anyway
- Better to configure backend properly from the start

### Option 2: Wildcard CORS (Allow All Origins)

```typescript
app.use(cors()); // Allows all origins
```

**Why we didn't choose this:**
- Security risk (especially in production)
- Better to be explicit about allowed origins

---

## Production Considerations

For production deployment, update CORS configuration to allow the actual frontend domain:

```typescript
const corsOptions = {
  origin: process.env.NODE_ENV === 'production' 
    ? 'https://reading-list-tracker.vercel.app'  // Production domain
    : 'http://localhost:5173',                    // Development domain
  credentials: true
};

app.use(cors(corsOptions));
```

Or use an environment variable:

```typescript
const corsOptions = {
  origin: process.env.FRONTEND_URL || 'http://localhost:5173',
  credentials: true
};
```

Then set `FRONTEND_URL` in production environment (Railway, Heroku, etc.).

## How to Prevent This in the Future

### For New Projects

1. **Install CORS immediately** when setting up Express backend
2. **Add to project template** - include CORS in initial setup
3. **Document in README** - mention CORS configuration in setup instructions

### Best Practices

- ✅ Always specify allowed origins explicitly (don't use wildcard in production)
- ✅ Use environment variables for origin URLs
- ✅ Test cross-origin requests early in development
- ✅ Keep CORS configuration near the top of middleware stack

### Checklist for Backend API Setup

```
[ ] Install express
[ ] Install cors and @types/cors
[ ] Configure CORS with allowed origins
[ ] Test API with frontend before building features
```

## Related Issues

### Similar Problems You Might Encounter

**1. CORS Errors Only on Specific Methods (POST, PUT, DELETE)**

**Symptom:** GET requests work, but POST/PUT/DELETE fail  
**Cause:** Preflight OPTIONS requests not handled  
**Solution:** CORS middleware handles this automatically

**2. CORS Errors Only in Production**

**Symptom:** Works locally, fails after deployment  
**Cause:** Frontend production URL not in allowed origins  
**Solution:** Update `corsOptions.origin` to include production URL

**3. Credentials/Cookies Not Being Sent**

**Symptom:** Authentication headers or cookies missing in requests  
**Cause:** `credentials: true` not set in CORS config  
**Solution:** Ensure both backend CORS and frontend fetch use credentials

## Lessons Learned

### What We Learned

1. **CORS is a browser security feature**, not a server error
   - API works fine from Postman/curl
   - Only browsers enforce CORS policy

2. **Different ports = different origins**
   - `localhost:3001` and `localhost:5173` are treated as separate domains
   - Port matters, not just hostname

3. **CORS should be configured early**
   - Don't wait until you try to connect frontend
   - Add it during initial backend setup

### Key Takeaway

> **For any backend API that will be accessed from a browser-based frontend, configure CORS immediately.**

Even if frontend and backend are eventually deployed together, CORS is needed for:
- Local development (different ports)
- Staging environments
- Production (may use CDN or separate domains)
